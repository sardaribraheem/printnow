## Product understanding

PrintNow is a mobile-first print-request marketplace for the NIIT community and nearby Lahore providers. Customers publish PDF, PNG or JPEG print requirements and compare independently priced offers from approved printers. Every offer lasts five minutes from database creation. The customer chooses a provider; acceptance atomically creates one order, reveals necessary contact information to the winner, and opens participant-only chat. The printer handles production and pickup or delivery. Payment is directly between customer and printer; launch commission and platform fees are zero.

An account may be both customer and printer. Admins manually approve providers and handle restrictions, disputes and operational failures. Eligible printers may review live-request documents with explicit customer consent, but cannot see exact customer contact/destination details before acceptance. Losing printers immediately lose future file access. Already viewed bytes cannot be recalled.

MVP includes the complete request-to-completion workflow, secure file processing, notifications, moderation and retention. Native Android screens have been added under the accepted mobile amendment. Integrated payments, commissions, courier APIs, ratings and office-document conversion remain deferred. Native push is planned separately and is not implemented.

## Confirmed upload scope and implementation defaults

Accept PDF, PNG and JPEG (`.jpg`/`.jpeg`). Other formats remain unsupported unless explicitly added. Keep the documented limits of three files, 25 MiB per file, 75 MiB combined and 200 printed sides per request, configurable for the pilot.

For images, each uploaded image is one logical page; copies and duplex settings use the same per-file counting rules as PDFs. Each file/copy starts on a new sheet: two separate image files do not silently become opposite sides of one sheet. Show this clearly in the preview and sheet total. Fit to the selected paper without cropping by default; preserve aspect ratio, apply EXIF orientation, flatten transparency onto white, and warn when effective print resolution is low. Do not infer physical print size from untrusted image metadata.

Validate actual file signatures and decoder output server-side, not just filename/MIME. Bound decoded pixels, dimensions, memory, processing time and previews; select concrete limits during M3 benchmarks. Strip metadata from generated previews/production derivatives and retain originals privately under the same access/retention policy. Produce an immutable, print-ready derivative with recorded settings so customers and printers review the same output. Provider production instructions must identify that approved derivative. Include originals, derivatives, previews and temporary outputs in deletion and access tests.

Image defaults above are implementation proposals within the confirmed format scope; record any later product changes explicitly.

## Architecture

Use a modular Next.js App Router application with TypeScript and Supabase Auth, Postgres, private Storage and Realtime. Follow the directory structure in `SPECs.md`. Pin supported stable package versions and commit a single lockfile. Use transactional database functions for business state changes, a shared server data-access layer for authorization and safe projections, and bounded workers for PDF/image validation, previews, outbox delivery and cleanup.

Maintain separate local/development, staging and production data. Version database schema, grants, RLS and functions in migrations. Privileged keys stay server-side. Use private, noncached file proxy responses with authorization on each request, including byte ranges. Store money as integer paisa and timestamps in UTC.

## Test and release strategy

Use unit tests for print counts, validation and domain rules; real Supabase/Postgres integration tests for RLS, grants, storage boundaries and atomic operations; concurrent database sessions for lock/expiry races; and mobile browser E2E for complete workflows. Map all acceptance IDs in `SPECs.md` to executed tests. Check real authenticated API/Storage/Realtime surfaces, not just hidden UI controls. Distinguish passed, skipped and blocked checks.

CI runs frozen installation, lint, typecheck, relevant unit/DB tests and production build. Staging release runs migrations, worker checks and complete E2E/security gates. Use synthetic PDFs, PNG/JPEG images and accounts. Do not run destructive tests against production or existing user data.

Prepare artifacts and test evidence before requesting any release approval. Production publication and paid infrastructure provisioning occur only within confirmed authorization. Store deployable migrations and environment setup/startup instructions in version control/configuration; never assume live development processes survive environment restoration.

## Pilot measurement

Aim for 30 completed paid jobs over two staffed weeks. Track the PRD's proposed learning thresholds: 80% of valid requests get an offer within five minutes; at least 50% get two providers; at least 90% of completed jobs meet the accepted timing; print-error/reprint rate at most 5%. Also measure acceptance reasons, repeat orders, provider participation, support time and actual hosting/storage cost. Any confirmed unauthorized file/address access pauses affected access pending repair.
